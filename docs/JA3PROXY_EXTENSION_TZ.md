# Техническое задание: расширение gocurl для запросов и TLS-отпечатков JA3Proxy

- Версия: 1.1
- Статус: проект ТЗ
- Целевой upstream: <https://github.com/ameshkov/gocurl>
- Связанный проект: JA3Proxy

## 1. Цель

Расширить gocurl так, чтобы он позволял из CLI или вызывающего Go-кода:

1. собирать HTTP-запрос из URL, метода, упорядоченных повторяемых заголовков и
   тела;
2. отправлять запрос напрямую либо через HTTP/SOCKS-прокси, в том числе через
   JA3Proxy;
3. выбирать TLS-профиль из экспортированного профиля JA3Proxy или задавать
   поддерживаемые параметры ClientHello вручную;
4. видеть фактические JA3, JA4 и нормализованные поля ClientHello,
   полученные из байтов отправленного рукопожатия;
5. автоматически сравнивать ожидаемый профиль с фактическим ClientHello и
   завершать команду с ошибкой при нарушении заданной политики.

gocurl расширяет профиль отправителя запроса. Сам JA3Proxy остаётся прокси и
регистратором. При запросе через HTTPS `CONNECT` TLS ClientHello формирует
gocurl, а JA3Proxy пересылает этот TLS-поток без изменения. Если включён
контролируемый TLS MITM, входящий и исходящий TLS — разные соединения:
профиль gocurl применяется к соединению клиент→JA3Proxy, а профиль JA3Proxy —
к соединению JA3Proxy→сервер.

## 2. Термины и границы отпечатков

- **HTTP-запрос** — метод, URL, заголовки и тело, отправляемые приложению.
- **TLS-профиль** — версия TLS, cipher suites, порядок/набор расширений, ALPN,
  SNI, группы, signature algorithms и иные поддерживаемые поля ClientHello.
- **Ожидаемый отпечаток** — значение профиля до соединения.
- **Фактический отпечаток** — JA3/JA4, вычисленные из байтов ClientHello,
  записанных непосредственно при отправке.
- **Профиль JA3Proxy** — версия TLS-шаблона, экспортированная в независимом
  версионированном JSON-формате.

JA3/JA4 относятся к TLS ClientHello. HTTP-заголовки, их порядок и поведение
HTTP/2 относятся к отдельному прикладному отпечатку и не должны называться
JA3/JA4. Для них в результатах нужны отдельные поля и статус проверки.

## 3. Объём работ

### 3.1. Формирование HTTP-запроса

Реализовать:

- URL с query-параметрами и корректным percent-encoding;
- все стандартные HTTP-методы и пользовательскую строку метода;
- ноль или более заголовков с сохранением порядка и повторений;
- тело из строки, stdin или файла без текстового преобразования байтов;
- явное управление автоматическими заголовками и значениями по умолчанию
  (`User-Agent`, `Accept`, `Content-Length`, `Content-Type`, `Accept-Encoding`);
- HTTP/1.1 и HTTP/2 с явным выбором версии и сообщением о фактически
  согласованном протоколе;
- существующие варианты прокси gocurl, включая HTTP CONNECT к HTTPS-узлу;
- поддержку отдельных параметров соединения с HTTPS-прокси и целевым
  HTTPS-сервером, если эти соединения оба используют TLS;
- вывод ответа в stdout/файл и JSON-результат с метаданными запроса.

Порядок заголовков является обязательным для HTTP/1.1-режима. Для HTTP/2
сохранять и проверять только те свойства порядка/кодирования, которые реально
контролируются выбранной реализацией; не обещать точный HTTP/2 wire fingerprint
без отдельного транспортного механизма и capture-теста.

### 3.2. TLS-профиль

Реализовать применение TLS-профиля к целевому TLS-соединению:

- встроенные уTLS-пресеты, доступные в закреплённой версии uTLS;
- импортируемые профили JA3Proxy типов PRESET, OBSERVED и CUSTOM, если все
  требуемые поля поддерживаются механизмом генерации;
- RANDOMIZED с явно записанным режимом и перечнем разрешённых случайных полей;
- точное применение поддерживаемых cipher suites, extension order, ALPN,
  supported groups, signature algorithms и версий TLS;
- отдельное SNI, только если это не конфликтует с политикой импортированного
  профиля;
- явное отклонение несовместимых или неподдерживаемых полей до установления
  соединения. Поля нельзя молча игнорировать или заменять настройками по
  умолчанию.

Случайные значения, GREASE, key share, PSK/session resumption и иные динамические
поля должны быть помечены как динамические. Проверка профиля использует правила
MUST/SHOULD/ignored из профиля; точное равенство сырых байтов не является
критерием для динамических полей.

Ручная отправка произвольного массива байтов ClientHello не входит в базовый
режим. Она допустима только отдельным явно обозначенным raw-режимом, если
последующее TLS-состояние и поддержка ответа сервера реализованы и проверены.

### 3.3. Разделение TLS-соединений и прокси

TLS-настройки прокси и TLS-настройки назначения независимы:

- `--proxy` выбирает маршрут запроса;
- `--proxy-tls-profile` (или эквивалентная опция) управляет TLS к HTTPS-прокси;
- `--tls-profile` управляет TLS к целевому HTTPS-серверу после CONNECT;
- SOCKS5 и незашифрованный HTTP-прокси не должны получать фиктивный TLS-профиль;
- для JA3Proxy в режиме туннеля захватываемый целевым сервером ClientHello
  должен соответствовать профилю gocurl;
- при MITM отдельно отражаются входящий и исходящий отпечатки, без смешивания
  их в один результат.

gocurl отражает только собственные TLS-соединения. Исходящий ClientHello
JA3Proxy при MITM доступен из recorder JA3Proxy, а не из gocurl. Сопоставление
двух сторон выполняется по идентификаторам тестового запроса и соединения;
отчёт gocurl не должен выдавать наблюдение прокси за своё.

### 3.4. Импорт профилей JA3Proxy

Добавить в JA3Proxy экспорт одного TLS-профиля в публичный документированный
формат, например `ja3proxy-client-profile/1`. Формат должен содержать:

- схему и версию профиля;
- имя, ID, версию, тип профиля, базовый preset и host patterns;
- поля ClientHello и порядок расширений;
- ALPN-политику;
- ожидаемые JA3, JA4 и TLS-NORM;
- MUST/SHOULD/constraints/ignored-dynamic;
- версию движка и сведения о совместимости;
- список неэкспортируемых или не поддерживаемых потребителем полей.

Формат не содержит пароли, приватные ключи, CA, локальные пути, содержимое
записей и другие секреты. gocurl не должен импортировать пакеты из пути Go
`internal/ja3proxy/...`; схема JSON является межпроектным контрактом и
версионируется независимо от внутренних Go-структур.

При загрузке профиля gocurl проверяет схему и все поля. Несовместимая версия
схемы или любое неподдерживаемое MUST-поле приводят к понятной ошибке с именем
поля. Неподдерживаемые необязательные поля также отображаются пользователю и
в JSON-результате.

### 3.5. Отчёт и верификация фактического ClientHello

Для каждого реально начатого TLS-рукопожатия сохранять/возвращать:

- выбранный профиль и его версию;
- URL, метод, прокси-маршрут и согласованный HTTP-протокол;
- ожидаемые и фактические JA3, JA3 hash, JA4 и TLS-NORM SHA-256;
- версии TLS engine, uTLS и формата экспорта;
- статус `MATCH`, `PARTIAL_MATCH`, `MISMATCH`, `UNSUPPORTED` или ошибку
  соединения;
- список различий по MUST/SHOULD/constraints;
- этап захвата: TLS к HTTPS-прокси или TLS к целевому серверу, включая
  соединение с JA3Proxy как MITM-сервером.

Отпечатки считаются по реально сериализованным/отправленным байтам ClientHello,
а не только по запрошенной структуре профиля. Опция проверки должна возвращать
ненулевой exit code для `MISMATCH`, нарушения MUST или неполного capture, если
пользователь запросил обязательное подтверждение.

`--json-output` сохраняет обратную совместимость существующего JSON-контракта:
новые поля добавляются без переименования текущих полей. Секретные заголовки
могут быть скрыты из отчёта по заданному пользователем списку имён; значение
по умолчанию не должно неожиданно удалять фактически отправленные заголовки из
обычного verbose-вывода без явного документированного правила.

## 4. Интерфейс CLI

Сохранить curl-подобные существующие ключи gocurl. Добавить согласованный набор
параметров, окончательные имена которого уточняются при реализации:

- `--tls-profile <file>` — профиль JA3Proxy JSON;
- `--tls-profile-check` — сравнить профиль с фактическим ClientHello;
- `--tls-profile-strict` — завершиться ошибкой при неподдерживаемом MUST-поле,
  mismatch или неполном захвате;
- `--proxy-tls-profile <file>` — профиль TLS-соединения к HTTPS-прокси;
- `--header-file <file>` — дополнительные заголовки в порядке файла;
- `--data-binary @<file>` и stdin — бинарное тело без перекодирования;
- `--request-header-order`/аналогичный механизм — явно сохранить порядок и
  повторы заголовков HTTP/1.1;
- `--json-output` — добавить в текущий JSON фактические request/TLS metadata.

Один профиль TLS задаётся одним способом за запуск. Если одновременно указаны
профиль и конфликтующие ручные TLS-флаги, команда отклоняет запрос до сети,
если пользователь не включил явно документированный режим переопределений.

## 5. API Go

CLI должен использовать публичный пакет gocurl, пригодный для встраивания:

- `Request` описывает URL, метод, упорядоченный список заголовков, тело и
  HTTP-настройки;
- `TLSProfile` описывает выбранный профиль, точку применения и политику
  сравнения;
- `Result` содержит HTTP-ответ и отчёт фактического TLS-профиля;
- конфигурация одного клиента не должна мутировать глобальные TLS-настройки
  другого клиента;
- транспорт должен корректно закрывать idle connections и освобождать ресурсы.

CLI и Go API используют один transport и единый код валидации профиля.

## 6. Этапы реализации

### Этап 1 — контракт и доказательство TLS-возможностей

1. Проверить текущую архитектуру gocurl и все места создания HTTP/TLS transport.
2. Зафиксировать совместимую версию uTLS и реализовать небольшой spike:
   preset, CUSTOM extension order, ALPN, proxy CONNECT и capture отправленного
   ClientHello.
3. Сверить вычисленные gocurl JA3/JA4 с независимым захватом и парсером.
4. Описать ограничения, в частности HTTP/2 header order и динамические поля.

Критерий перехода: spike доказывает управление target ClientHello через
поддерживаемые прокси и воспроизводимо получает actual fingerprints.

### Этап 2 — экспорт/импорт профиля и CLI

1. Утвердить JSON-схему экспорта профиля JA3Proxy.
2. Реализовать экспорт и импорт, проверки совместимости, MUST/SHOULD и отчёт.
3. Добавить CLI параметры и сохранить совместимость существующего gocurl.
4. Добавить golden профили и версии схемы.

### Этап 3 — запросы, HTTP API и транспортная диагностика

1. Поддержать упорядоченные и повторяемые заголовки HTTP/1.1 и бинарные тела.
2. Подтвердить HTTP/2 свойства отдельно от JA3/JA4.
3. Добавить публичный Go API, JSON output и раздельные отчёты для TLS-сегментов.
4. При необходимости отдельным подпунктом добавить HTTP/2 fingerprint
   customization; не объявлять его готовым на основании одного TLS-профиля.

### Этап 4 — интеграция JA3Proxy и выпуск

1. Добавить экспорт профиля и документацию в JA3Proxy.
2. Добавить безопасные локальные интеграционные сценарии с HTTP CONNECT,
   SOCKS5 и TLS MITM.
3. Подготовить fork PR upstream без смешивания изменений JA3Proxy и gocurl.
4. Документировать версионную совместимость, примеры и диагностику несовпадения.

## 7. Требования к тестированию

### Unit-тесты

- JSON-схема: валидный профиль, неизвестная версия, отсутствующие обязательные
  поля, неизвестные поля, несовместимые переопределения;
- сохранение порядка и повторов HTTP/1.1 заголовков;
- бинарное тело: пустое, нулевые байты, большой потоковый файл;
- корректное разделение proxy TLS и target TLS конфигураций;
- соблюдение MUST/SHOULD и обработка динамических полей.

### Интеграционные тесты

- локальный TLS endpoint захватывает сырые ClientHello bytes;
- запрос прямой и через HTTP CONNECT/SOCKS5 проходит с тем же target TLS
  профилем;
- HTTPS proxy использует отдельный ожидаемый TLS-профиль;
- сервер независимо вычисляет JA3/JA4 из capture и сравнивает с отчётом gocurl;
- JA3Proxy recorder получает соответствующее входящее наблюдение;
- TLS MITM создаёт две записи в recorder JA3Proxy с разными leg ID; отчёт
  gocurl сопоставляется с входящим leg, а исходящий leg проверяется отдельно;
- перестановка или неподдержанное обязательное расширение вызывает ожидаемый
  `MISMATCH`/`UNSUPPORTED`, а не ложный `MATCH`.

Для тестов не обращаться к публичным целевым сайтам. Использовать только
локальные TLS endpoints с тестовыми ключами/сертификатами.

## 8. Критерии приёмки

Работа принимается, если:

1. существующие сценарии gocurl продолжают работать без TLS-профиля;
2. HTTP method, ordered/repeated headers и binary body соответствуют заданным;
3. gocurl загружает экспортированный профиль JA3Proxy либо ясно объясняет
   каждое неподдерживаемое поле;
4. actual JA3/JA4 рассчитаны из отправленных ClientHello bytes;
5. фактический capture совпадает с ожидаемым профилем по его MUST-политике, либо
   команда явно завершает проверку несовпадением;
6. разные TLS-сегменты прокси не смешиваются;
7. JSON и Go API возвращают документированный отчёт;
8. локальные интеграционные тесты проходят на поддерживаемых ОС;
9. README документирует ключи, профильный JSON, прокси-сценарии и ограничения
   HTTP/2/HTTP/3.

## 9. Явно исключено из первой поставки

- изменение рабочей маршрутизации или TLS-профилей JA3Proxy при запуске gocurl;
- автоматическая выдача/установка CA и отключение проверки сертификатов;
- произвольное изменение TCP/IP stack fingerprint (например, JA4T), поскольку
  он формируется ниже уровня HTTP/TLS-клиента;
- заявление о точном browser fingerprint только на основании совпавших JA3/JA4;
- незаметное игнорирование неподдерживаемых полей профиля.

Поддержку HTTP/3/QUIC ClientHello/transport fingerprints и полное управление
HTTP/2 framing требуется оформить отдельными критериями, если они входят в
целевой профиль использования.

## 11. Контракт запроса и маршрута

1. Внутреннее представление HTTP/1.1 запроса — упорядоченный список
   `{name, value}`, а не `http.Header`. Оно сохраняет регистр имени, порядок и
   повторения до записи в соединение. Режим точного порядка реализуется
   отдельным writer/transport, если стандартный `net/http` не даёт требуемых
   гарантий. Парсер отклоняет CR/LF внутри имени или значения.
2. `Host` и request-target задаются отдельно от обычных заголовков. Явно
   определить origin-form для запроса к целевому серверу, authority-form для
   `CONNECT` и absolute-form только там, где его требует HTTP-прокси.
   `--connect-to`/`--resolve` меняют адрес соединения, но не подменяют
   Host/SNI без отдельной команды.
3. Политика автоматических заголовков имеет два документированных режима:
   совместимый с нынешним gocurl и точный. В точном режиме необъявленные
   User-Agent, Accept-Encoding и Content-Type не добавляются. Конфликты
   `Content-Length`/chunked, Host и повторяемых hop-by-hop заголовков
   отклоняются до отправки. Итоговый порядок проверяется захватом HTTP-байтов.
4. Тело из файла/stdin передаётся без преобразования байтов и без обязательной
   загрузки целиком в память. Повторная отправка тела при retry/redirect
   разрешена только для воспроизводимого источника; иначе возвращается явная
   ошибка. Правила для пустого тела, нулевых байтов и вычисления длины
   закрепляются отдельными тестами.
5. Заголовки к `CONNECT` задаются отдельной опцией от заголовков целевого
   запроса. Учётные данные прокси никогда не попадают в target request.
   Для SOCKS5 и SOCKS5H сохраняется их текущая семантика разрешения DNS.
6. Redirect по умолчанию не должен незаметно менять измеряемый target:
   каждый разрешённый переход — отдельный request/connection record с URL,
   методом, Host, SNI и новым либо повторно использованным TLS-соединением.

## 12. Межпроектный формат профиля

Версию `ja3proxy-client-profile/1` закрепить в JSON Schema и golden fixtures.
Экспортирует JA3Proxy, импортирует gocurl. Одно значение файла — один снимок
версии профиля. Обязательные поля верхнего уровня:

| Поле | Тип и смысл |
| --- | --- |
| `schema_version` | Строка `ja3proxy-client-profile/1`; неизвестную major-версию отклонять. |
| `id`, `version`, `name`, `profile_type` | Идентичность неизменяемого снимка; тип из `PRESET`, `OBSERVED`, `CUSTOM`, `RANDOMIZED`. |
| `fields` | Порядковые массивы `cipher_suites`, `extension_order`, `supported_versions`, `supported_groups`, `signature_algorithms`, `alpn`; политики `alpn_policy`, `custom_alpn`, `alps_policy`, `custom_alps`, `padding_length` по применимости. |
| `policy` | `must_match`, `should_match`, `ignored_dynamic`, `constraints` с путями в нормализованном ClientHello. |
| `expected` | `ja3`, `ja3_hash`, `ja4`, `normalized_sha256`, `normalization_version`, `materializer_version` и версия алгоритма JA3/JA4. |
| `engine` | Имя и закреплённая версия генератора ClientHello, версия экспортёра и сведения о совместимости. |

`base_preset`, `host_patterns`, режим RANDOMIZED и исходное наблюдение
передаются как отдельные метаданные. `host_patterns` не переключает профиль
автоматически при одном вызове gocurl. В `OBSERVED` и `CUSTOM` исходный
ClientHello может содержать не воспроизводимые через uTLS поля: экспортёр
указывает `replayability`, а импортёр возвращает `UNSUPPORTED` для любого
необходимого, но не материализуемого поля. Формат не включает токены, ключи,
сертификаты, сырое содержимое сессий и локальные пути.

Начальную совместимость проверить с uTLS `v1.8.2`, закреплённой в JA3Proxy, и
версиями Go обоих проектов. Это целевая версия для тестов, а не обещание
равенства отпечатков после обновления движка: обновление требует повторного
прогона golden-профилей и локальных capture-тестов.

Списки и политика берутся из `tlsprofile.Template`, но JSON Schema является
самостоятельным публичным контрактом. Неизвестное обязательное поле,
неизвестный путь MUST и неразрешённое расширение отклоняются до сети. Для
каждой версии формата нужны минимум один корректный пример, один пример
`UNSUPPORTED`, тест чтения предыдущей совместимой версии и проверка
одинаковых результатов экспортёра и импортёра.

## 13. Границы TLS-наблюдения и совместимость режимов

1. Захват привязывается к конкретному TLS-соединению и выполняется на пути
   отправки. Парсер собирает полное handshake-сообщение ClientHello через
   границы TLS records и нескольких `Write`, в том числе с
   `--tls-split-hello`. Успех сериализации без успешной отправки не считается
   фактическим wire-наблюдением.
2. HelloRetryRequest или повторное рукопожатие создают отдельные записи
   ClientHello с порядковым номером. Если соединение повторно использовано и
   ClientHello не отправлялся, результат помечается `REUSED_CONNECTION`, а не
   `MATCH`. До отправки — `NOT_OBSERVED`, неполный захват — `INCOMPLETE`.
3. JA3, JA4 и TLS-NORM рассчитываются одним согласованным с JA3Proxy
   алгоритмом; версии нормализации и правила удаления GREASE фиксируются в
   отчёте. Совпадение только JA3/JA4 не заменяет проверку MUST-полей.
4. ALPN после handshake проверяется против выбранного HTTP transport.
   Несовместимый ALPN или невозможность выполнить выбранную версию HTTP —
   ошибка, а не тихий переход на другую версию. Для HTTP/2 отдельно указывать
   предел контроля pseudo-headers, SETTINGS, окон и порядка фреймов.
5. `--ech`, `--echgrease`, экспериментальный PQ, WebSocket, OHTTP и HTTP/3
   проходят матрицу совместимости с новым TLS engine. До доказанной поддержки
   профиля в конкретном режиме сочетание отклоняется до сети с названием
   несовместимых опций. Для ECH внешний наблюдатель видит outer ClientHello;
   inner ClientHello не выдаётся за наблюдаемый на линии. Для OHTTP отчёт
   относится к TLS до gateway, а не к скрытому target.
6. Для TLS к HTTPS-прокси и к target нужны разные записи и разные политики
   проверки. В JSON каждый handshake содержит `connection_id`, `leg`,
   `attempt`, `hello_index`, `capture_status`, ожидаемые/фактические значения
   и различия. API не использует общий изменяемый `last connection` для
   параллельных запросов.

## 14. Порядок приёмки и критерий полноты

1. Сначала утвердить JSON Schema, статусы наблюдения и матрицу совместимости.
2. Подтвердить локальным capture-тестом target ClientHello для прямого
   соединения, HTTP CONNECT и SOCKS5; отдельно — proxy TLS через HTTPS-прокси.
3. Подтвердить HTTP/1.1 request bytes: порядок, регистр, повторения заголовков,
   Host, тело, длину и CONNECT-заголовки. Тесты сравнивают именно полученные
   сервером байты, а не только собранный объект Go.
4. Проверить conflict matrix (`--tls-profile` с ручными TLS-флагами,
   `--http3`, ECH/PQ, ALPN, прокси без TLS), все классы статусов,
   повторный ClientHello, redirect и отсутствие нового handshake при reuse.
5. Успешный TLS-профиль означает лишь совпадение заявленных TLS-полей.
   «Полностью заданный HTTP/2 отпечаток» можно объявить только после тестов
   SETTINGS, pseudo-header order и framing; HTTP/3/QUIC — после отдельных
   capture-тестов QUIC. TCP/IP и JA4T остаются вне возможностей gocurl.

Изменение считается готовым после прохождения локальных golden/capture-тестов,
`make check`, `go vet ./...` и проверки, что прежние CLI сценарии gocurl без
профиля дают прежний результат. Интеграционные тесты новых функций должны быть
локальными и не зависеть от публичных DNS/HTTP-сервисов. Поддерживаемая
комбинация всегда выдаёт результат и отчёт; неподдерживаемая — понятную ошибку
до сети.

## 15. Минимальные машинные контракты CLI и отчёта

- `--header-file` принимает UTF-8 файл, одна строка — один заголовок в форме
  `Name: value`. Пустые строки пропускаются; строки с невалидным именем,
  встроенными CR/LF либо без двоеточия отвергаются с номером строки. Порядок
  этого файла относительно повторяемых `-H` фиксируется документацией и
  проверяется тестом.
- `--data-binary @file` и `--data-binary @-` означают файл и stdin. Параметр
  `--data` сохраняет прежнюю семантику. При одновременном указании двух
  источников тела команда сообщает конфликт до установления соединения.
- JSON добавляет массив `connections`, не удаляя существующие поля ответа.
  Каждый элемент указывает `connection_id`, `leg`, `attempt`, `hello_index`,
  `capture_status`, `expected`, `actual`, `diff`, `engine_version` и
  `normalization_version`; `actual` отсутствует при `NOT_OBSERVED` и
  `REUSED_CONNECTION`. Секреты и сырые handshake bytes в JSON по умолчанию не
  включаются.
- Коды завершения закрепить до выпуска: `0` — запрос и требуемые проверки
  успешны; `2` — ошибка аргументов/профиля либо `UNSUPPORTED`; `3` — TLS/HTTP
  ошибка соединения; `4` — `MISMATCH` или нарушение MUST; `5` — `INCOMPLETE`
  при обязательной проверке. Без `--tls-profile-check` отсутствие capture
  явно отражается в JSON, но само по себе не меняет успешный код запроса.
- Флаг `--tls-profile-strict` включает проверку даже без отдельного
  `--tls-profile-check`; такая комбинация не должна молча завершаться кодом
  `0`. Текст ошибки, JSON status и exit code выражают одну причину.
