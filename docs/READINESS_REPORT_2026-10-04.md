# Анализ готовности goCURL на 4 октября 2026 года

## Вердикт и границы проверки

Основной функционал работает в проверенных локальных сценариях. Однако проект
ещё не готов к завершению ТЗ и выпуску: подтверждены три группы функциональных
дефектов, не проходит контроль качества и не обеспечена воспроизводимость
текущей реализации из закоммиченного состояния. Остались не только тесты.

Объект проверки — `C:\ja3proxy\gocurl`, активный подпроект из текущего задания.
Это не заключение о готовности всего JA3Proxy, его веб-панели и интеграции.
Проверена рабочая копия на ветке `main`; HEAD —
`2e994bef1f4f6490a5c42fa4e906de1a354f3bf5`.
Изменения рабочей копии входят в аудит, но не входят автоматически в этот коммит.

Навигация по связям выполнялась через GitNexus; его индекс старше текущих
незакоммиченных изменений. Поэтому выводы сверены с локальным исходным кодом,
тестами и отдельными воспроизведениями. Номера строк ниже относятся к этой копии.
Исходники и статусы ТЗ в ходе аудита не изменялись; создан только этот отчёт.

## Что уже реализовано

| Область | Подтверждённые возможности |
| --- | --- |
| HTTP/1.1 | Порядок и повторы заголовков, свой request-target, отключение стандартных заголовков, бинарные тела из файла/stdin, политика redirect/retry |
| TLS поверх TCP | Пресеты и профиль ClientHello, параметры TLS, захват фактического ClientHello, JA3/JA4/TLSNORM, сравнение и строгие режимы |

| HTTP/2 | Документированный набор SETTINGS и их порядок, порядок псевдозаголовков/заголовков, фрагментация и padding, размер DATA, настройки начального потока и PRIORITY |
| HTTP/3 и QUIC | QUIC v1/v2, поддерживаемые transport parameters и их порядок, явные нули, параметры Initial/CID, расширенные SETTINGS и datagrams |
| Маршруты | Прямые соединения, поддерживаемые HTTP(S)/SOCKS-маршруты, WSS и OHTTP; локальные проверки соответствующих TLS-режимов |

Табличное соответствие полей API не заменяет проверку поведения каждого поля
на реальном соединении. Воспроизведения ниже показывают пробелы именно в этом.

### Ограничения согласованного профиля

Выбран документированный управляемый профиль, а не побайтовый replay любого
браузерного capture. Следующие ограничения сами по себе не являются новыми
незакрытыми требованиями без расширения согласованного объёма:

- HTTP/2 не предоставляет произвольный replay HPACK/кадров, полный планировщик
  потоков и произвольное управление всеми окнами flow control.
- QUIC использует `crypto/tls`, а не произвольный uTLS ClientHello; не обещает
  полного повторения любого пакета или всего браузерного QUIC-отпечатка.
- HTTP/3 через HTTP(S)-прокси не поддерживается; предусмотрены подходящие
  прямые и SOCKS UDP-маршруты.
- WebSocket ограничен HTTP/1.1; API не является полноценной библиотекой
  управления всеми разновидностями WebSocket framing.
- PQ не поддерживается для HTTP/3 и импортированного TLS-профиля по текущему
  контракту. Ошибки ниже относятся к нарушению этого контракта, не к просьбе
  незаметно расширить его.

Поэтому утверждение «можно формировать абсолютно любые запросы и отпечатки»
для текущей реализации неверно.

## Подтверждённые функциональные дефекты

### 1. P1: конфликт импортированного TLS-профиля с PQ не отклоняется

В `internal/config/config.go:667` проверяется непустое значение
`cfg.Experiments[ExpPostQuantum]`, а `parseExperiments` сохраняет обычный
`--experiment=pq` с пустым значением. Наличие ключа и непустое значение здесь
не эквивалентны.

Воспроизведение: импортированный профиль
`internal/client/utlsengine/testdata/profile-v1-valid.json`,
`--experiment=pq` и адрес `https://127.0.0.1:1/` проходят проверку конфигурации.
Вместо ошибки несовместимых параметров получается отказ TCP-соединения
с кодом результата 3.

В `internal/client/clientdialer.go:156` ветка импортированного профиля
выбирается раньше ветки PQ. Несовместимая комбинация доходит до сетевого
выполнения, вместо отказа до подключения. Фактическое согласование PQ этим
воспроизведением не проверялось.

Для CLI дефект воспроизведён. Влияние на API с `TLSProfile.ProfilePath`
установлено по общему пути ParseConfig; отдельное воспроизведение API не
выполнялось. Запрет для `TLSProfile.ClientHello` не закрывает вариант ProfilePath.
В тестовой таблице несовместимых TLS-параметров отсутствует эта комбинация.

### 2. P1: CLI разрешает HTTP/3 + PQ, хотя API запрещает

`pkg/gocurl/client.go:723` отклоняет эту комбинацию. Общая CLI-конфигурация
соответствующей проверки не содержит и выбирает HTTP/3 transport.

Воспроизведение с `--http3 --experiment=pq --connect-timeout 1`,
`--json-output --insecure` и `https://127.0.0.1:1/` заканчивается сетевым
таймаутом QUIC с кодом 3. Нужен отказ конфигурации до обращения к сети,
согласованный для CLI и API.

Это подтверждённое расхождение API/CLI и пробел отрицательной матрицы
совместимости, даже при успешных позитивных тестах маршрутов.

### 3. P1: ConnectTimeout не ограничивает установление целевого TLS/QUIC

`internal/client/clientdialer.go:620` преобразует ConnectTimeout для socket dial.
Ограничение не распространяется надёжно на последующее целевое рукопожатие.
В `DialQUIC` вызовы `quic.DialEarly` используют контекст без добавленного
ConnectTimeout. Для обычного TLS `handshakeTLS` на строках 596–603 вызывает
`Handshake()` без контекста. HTTP/1.1–HTTP/2 transport использует собственный
DialTLSContext без компенсирующего общего deadline этого этапа.

Два воспроизведения отдельным собранным бинарником, без времени компиляции:

- Loopback UDP-сервер, не отвечающий на QUIC: при `--connect-timeout 1`
  завершение с сетевой ошибкой наступило через 5104 мс, а не около 1000 мс.
- Loopback TCP-сервер, не отвечающий на TLS, режим `--http1.1`: при том же
  таймауте процесс ещё работал спустя 3056 мс. Диагностический процесс был
  остановлен после контрольного ожидания; конечное время не измерено.

Временные диагностические бинарники удалены. Проверялся только управляемый
локальный сервер, без внешнего трафика.

Имеющийся тест ConnectTimeout для TLS самого HTTPS-прокси не покрывает
рукопожатие целевого сервера и QUIC. Влияние на API предполагается из общего
transport; отдельный API-тест нужен для закрепления контракта. При исправлении
важно также проверить отмену контекста и закрытие неудавшегося соединения.

## Воспроизводимость и поставка

На момент проверки до создания отчёта рабочая копия содержала:

- 30 изменённых отслеживаемых файлов;
- 63 прочих неотслеживаемых файла;
- 1922 неотслеживаемых файла vendor;
- всего 2015 записей состояния; среди них 51 Go-файл вне vendor.

`pkg/gocurl`, `vendor`, `main_test.go` и
`internal/config/header_file_test.go` отсутствуют в списке отслеживаемых файлов.
Следовательно, успешная сборка этой рабочей копии не доказывает возможность
собрать весь текущий функционал из коммита HEAD. Это блокер P0 для поставки.
После создания отчёта число неотслеживаемых файлов увеличится на один.

Локальное сравнение с кэшированным `origin/main` показывает `0 0`.
Свежая проверка `git ls-remote origin refs/heads/main` не удалась из-за SSL/TLS
ошибки schannel. Актуальный HEAD на GitHub и доставку текущих изменений
эта проверка не подтверждает. В ходе анализа push не выполнялся.

Нужно отдельно подготовить полный воспроизводимый коммит исходников и
документированных патчей зависимостей, затем проверить чистую рабочую копию.
Не следует автоматически добавлять все неотслеживаемые файлы: базы, ключи,
реальные captures и локальные кэши должны остаться вне репозитория.

Для пункта 2 найденный CLI-тест успешного захвата проверяет OBSERVED, а не
MATCH импортированного профиля. Строгий NOT_OBSERVED проверяется внутренним
тестом с вручную собранной конфигурацией; применимость такого сочетания
через публичный parser следует явно описать, не требовать невозможный режим.

Для пункта 5 не найден объединённый API-тест автоматического получения ECH
через DNS с последующим принятым ECH. Есть отдельные resolver-тесты и принятый
ECH с явно переданной конфигурацией. Для документированных зашифрованных DNS
режимов нужно определить и закрыть необходимую API wire-матрицу; сопоставления
CLI-аргументов недостаточно. IPv6-only тест в этой среде остаётся пропущенным.

Текущие fuzz-цели: ClientHello fingerprint parser, capture TLS records и
header-file parser. Длительная новая fuzz-сессия в этом аудите не проводилась.
План пункта 8 также включает profile JSON/constraints, HTTP/2 SETTINGS/order,
QUIC parameters/order и SOCKS address parser.

Конкретные документационные расхождения:

- README предлагает установку и бинарники upstream `ameshkov`, а не сборку
  данной реализации с обязательным локальным патчем vendor.
- Общее утверждение README о неподконтрольном порядке QUIC-параметров
  противоречит реализованному управлению порядком части параметров.
- Утверждение о захвате только первого ClientHello не отражает HRR-поддержку.
- AGENTS утверждает, что тесты не запускают бинарник; CLI helper-process
  тесты уже существуют.
- Markdown ТЗ не проходит проверку из-за оформления списков и таблиц,
  в частности около строк 277 и 317.

## Порядок завершения

1. Закрыть P0 воспроизводимости: отобрать необходимые исходники и vendor,
   проверить сборку и тесты из чистого состояния на `main`.
2. Исправить три группы поведенческих ошибок выше. Добавить отрицательные
   тесты конфликтов CLI/API и локальные тесты deadline целевого TLS/QUIC.
3. Восстановить работоспособность полного lint без отключения нужных проверок;
   устранить подтверждённые ошибки форматирования и Markdown, пройти gate.
4. Дополнить матрицу публичного API/CLI: успешный MATCH, применимые строгие
   статусы, согласованные DNS/ECH-сочетания, проверяемый IPv6-сценарий.
5. Выполнить CI на заявленных ОС и Go 1.26.5; отделить ограничения машины
   от дефектов продукта, приложить проверяемые результаты.
6. Завершить fuzz parsers из backlog и зафиксировать воспроизведение проверок.
7. Согласовать документацию с реальными возможностями и подтверждёнными
   статусами. Затем заниматься косметикой.

Исправления этих дефектов не требуют добавления лишней защиты локального
режима или новых несогласованных функций. После изменений нужны повторные
регрессионные проверки; успешные результаты текущей копии не переносятся
автоматически на будущие правки.

## Что этим аудитом не подтверждено

Не проверены актуальное содержимое GitHub, чистая сборка полного текущего
функционала из коммита, CI всех ОС, точная версия Go из CI, длительная fuzz-
кампания и внешние opt-in проверки. Не заявляется отсутствие всех возможных
ошибок: зелёный race-набор не отменяет подтверждённые поведенческие дефекты.

Практический итог: локально пользоваться проверенными режимами уже можно,
учитывая найденные ограничения таймаута и несовместимые параметры. Объявлять
проект полностью готовым по ТЗ или выпускать как завершённый пока нельзя.
